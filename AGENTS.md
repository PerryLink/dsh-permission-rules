# AGENTS.md

Standalone DeepSeek Harness plugin repository (`dsh-permission-rules`). Development follows the dsh-plugin-guide skill and the official plugin contract; this file records repo-local decisions.

## Layout

- `src/index.ts` — function-plugin contract (`name`/`inject`/`Config`/`apply`; NO default export — the Loader unwraps `exports.default ?? exports`). Injects `commands` + `tools`.
- `src/config.ts` — Schemastery schema + explicit `resolveConfig` (no hidden `?? default` in `run()` paths); closed enums and boolean flags are validated at resolution so plain-JS mounts fail loud too.
- `src/glob.ts` — strict glob→RegExp compiler + the backtracking guards: `maxGlobStars` caps unbounded star expansions, and regex-mode patterns reject nested unbounded quantifiers and quantified overlapping literal alternations. Bad patterns throw at compile time (load), never silently match nothing.
- `src/rules.ts` — the pure core: YAML document validation, pattern compilation (incl. `!pattern` negation), first-match evaluation, the `agents` identity dimension (`main`/`subagent`/`preset:<name>` selectors against session-header candidates; unknown identity never matches — fail closed), nested path-candidate extraction, `when`/`absent` dimensions, chain merging (`compileRulesChain`), shadow detection (`findUnreachableRules`). No fs/clock/process state.
- `src/prose.ts` — `/rules` output vocabulary in five languages (`en`/`zh` reference, `es`/`pt`/`hi` community) + `describeRule` dimension tokens (incl. the `src` source-attribution token). Rule `reason`s are never translated.
- `src/events.ts` — `permissionRules/decision` SessionEventMap member (declaration merging, incl. the `outcome` field) + `AuditAppend`, the append surface that requests the envelope's `ignorable: true` marker. The request is a probe, not a guarantee: every build from the alpha.5 surface on (the `0.1.2-rc`, `0.1.3-alpha` and `0.1.5-alpha` lines) accepts the third argument and silently discards it.
- `src/runtime.ts` — `tools/pre-execute` listener, per-cwd rule-chain loading (project chain by cwd / `searchUp` walk → fallback → empty), `permissionRules/decision` audit, `/rules` command (`list | reload | decisions [n] | test [flags incl. --platform]`), Chokidar watch (LRU cache with resolved/case-folded keys, watcher reconciliation, timer cleanup, candidate watches on expected-but-absent rule files so mid-session creation is adopted). Registers itself as `ctx.permissionRulesRuntime`.
- `test/` — vitest; real `Context` + real `Session`/`Commands`/`ApprovalService` from the pinned `0.1.5-alpha.1` dev peers (whose `Session.append` still cannot stamp the marker, so `audit-support.spec.ts` covers the degradation gate against the real installed peer and simulates the older lines through the `peerVersion` seam); `repair-session-logs.spec.ts` runs the shipped script on `%TEMP%` fixtures across every log generation; chokidar mocked with a fake EventEmitter; the dsh-auto-review integration uses its tarball with a scripted reviewer mock.
- `docs/rules-format.md` (+ `.en.md`) — the rule file schema and the 5-rule security baseline; `docs/rules-format.schema.json` is the machine-readable schema for editor completion.
- `scripts/repair-session-logs.mjs` — one-off repair for session logs written before the marker: rewrites targeted audit rows to carry `ignorable: true` (frame-preserving zstd rewrite, backups, `scan`/`repair`/`--dry-run` modes), or removes them outright in `strip` mode for harness lines that refuse marked plugin events (the `0.1.2-alpha` line). It discovers every generation-addressed basename by the canonical `session[.vN].jsonl[.zstd]` form (`session.jsonl` for v0/v1, `session.v2.jsonl` for the `0.1.3-alpha` line, `session.v3.jsonl` for the `0.1.5-alpha` line) and carries the `0.1.5-alpha.1` harness catalog plus the v1/v2-only spellings (`assistant/chunk`, `tool/code-dispatch`, `tool/code-dispatch-start`; V3 renamed the latter two to `tool/ptc-dispatch`). `strip` order: v1 logs before a 0.1.3-or-later host opens them (the v1→v2 migration refuses unknown v1 events even when marked) and v2 logs before a `0.1.5-alpha` host migrates them (the v2→v3 gate refuses every unclassified event even when marked); native v3 logs accept marked rows and only need `repair`.
- `scripts/check-readme-sync.mjs` — five-language README sync gate (section structure, config-table keys, `/rules` command docs); wired into CI.
- `.github/ISSUE_TEMPLATE/*` + `.github/PULL_REQUEST_TEMPLATE.md` + `SECURITY.md` — structured issue forms (bug/feature), PR checklist, and the private vulnerability-reporting policy.

## Hard rules applied here

- Waterfall listener (`tools/pre-execute`) always calls `next()` unless it claims the call with `deny`/`ask`. An `allow` hit is NEVER short-circuited. Under `enforce: false` (dry-run) even deny/ask hits delegate — the record keeps the would-be action with `dryRun: true` plus the real downstream `outcome`.
- Model-visible ⟺ logged: the only model-visible plugin content is the deny/ask reason materialized by the tools registry into the tool result; the `permissionRules/decision` audit event carries the same `callId` and reason for reconstruction, and its `outcome` records the FINAL pre-execute decision (an allow hit followed by a downstream deny is logged as denied).
- Log-only audit: `permissionRules/decision` is never injected into the model context, and is appended with `{ ignorable: true }` via the `AuditAppend` surface. The `0.1.0-rc.8`+ line stamps the marker; the `0.1.0-rc.1`–`rc.7` and `0.1.1-rc.1`–`rc.7` lines silently drop it, the `0.1.2-rc` line ships the alpha.5 surface (its `Session.append` cannot stamp the marker either), the `0.1.2-alpha` line refuses plugin events on read even when marked, the `0.1.3-alpha` line keeps the same surface-only append signature (verified against the `dsh-v0.1.3-alpha.1` tag), and the `0.1.5-alpha` line drops the third argument the same way (verified on the published `0.1.5-alpha.1` package, whose envelope field survives for stored-log reads only) — so the runtime detects unsafe hosts BEFORE the first append (peer-version pre-check, then a probe of the appended envelope's return value) and disables session-log audit with a one-time warning — `allowUnmarkedAudit: true` opts back in, and `scripts/repair-session-logs.mjs` repairs already-polluted logs (its `strip` mode removes audit rows where the marker cannot help; strip v1 logs before a 0.1.3-or-later host opens them and v2 logs before a `0.1.5-alpha` host migrates them, while native v3 logs only need `repair`).
- Loud misconfiguration: invalid YAML, unknown fields/actions, bad globs/regexes, backtracking-prone patterns, and rule counts over `maxRules` fail the load (`badFilePolicy` chooses fail vs ignore-with-warning). Deployment-level files (absolute `rulesFile`, `fallbackPath`) fail the mount. `searchUp` + absolute `rulesFile` fails `resolveConfig`.
- Backtracking bounds: a compiled glob's degree equals its star count — `maxGlobStars` (default 2) caps it exactly; regex mode rejects nested unbounded quantifiers and quantified overlapping literal alternations, while independent quantifier chains stay allowed (documented escape hatch).
- Line endings are normalized before parsing: `parseRulesDocument` maps CRLF onto LF, drops a stray CR inside a line, and treats every CR as a line separator in a CR-only file, so a rule file authored or checked out on the Windows side parses to the same document as its LF twin. A lone CR is NOT a line break to the YAML parser in every position — it survives into the scalar it terminates (`domains: [registry.npmjs.org\r]`, or a final line ending in a bare CR), which compiled a pattern that silently never matched its target (issue #19 item 4).
- Agent identity is derived only from the session header (`origin: 'subagent'`, `agentPreset`): `main`/`subagent`/`preset:<name>` candidates. Unknown identity (agentless or header-less) yields no candidates, so `agents`-scoped rules fail closed and never match an unidentified caller.
- Watch failures warn only: a bad HMR reload keeps the previous rules and never crashes the process.
- Session-less proxy traffic is judged against the CONFIGURED chain, never an empty map: `hostChain()` loads the chain for the host process's own working directory (project file → absolute `rulesFile` → configured fallback → shipped baseline) and `proxyChains()` consults it while no per-cwd chain is loaded — so the harness's own boot-time host-level fetches (the plugin market's catalog/update/npm lookups) already honour an allow rule that is configured (issue #18). The host chain is deliberately not a `byCwd` member and is not watched, so a session workspace chain always outranks it and the first tool call of any session takes over with the normal watched chain; an unusable configured chain warns once and degrades to the mode default (fail closed).
- WSL/drvfs watches poll: `watchPollingFor` switches a watch to `usePolling` (300 ms interval) when the watched rule file is under `/mnt/<drive>` or `/proc/version` reports a Microsoft kernel, because chokidar's native change events are unreliable on drvfs/9p and a rule edit otherwise stops hot-reloading silently, with no error (issue #19 item 1). Detection is per watch, so every other host keeps the native watcher; `/rules reload` stays the manual fallback.
- Expected-but-absent rule files (project file not in effect, deleted fallback) are watched through their deepest existing ancestor directory — chokidar cannot reliably watch a missing path whose parent is also missing — so a file created mid-session is adopted without a manual reload. Candidate watchers never recurse past that ancestor's immediate children: when the walk-up lands on the workspace root (e.g. no `.dsh/`), the watcher runs `depth: 0` with `node_modules`/`.git` ignored (issue #13), upgrades itself when the missing path component appears, and closes when its watched directory disappears. Under `searchUp` only the immediate cwd-level candidate is watched; deeper ancestors need `/rules reload`. The per-workspace cache key is `resolve(cwd)` case-folded on Windows, so differently-spelled paths to one workspace share one entry and one watcher set.
- No reviewer subagents, no model calls, no OS-sandbox changes — `ask` ends at the official approval seam; the answerer role belongs to `dsh-auto-review`.
- **The injected proxy environment does NOT reach the host's own outbound requests — corrected 2026-09-10 after measurement.** The injection covers spawned shell children (its documented purpose) and any consumer that reads the proxy names at request time. It does not cover the host process's `fetch`-based traffic: the launcher installs undici's global dispatcher from the **launch environment** before the first plugin mounts (`apps/cli/src/profile-boot.ts`), `packages/util/http-proxy/src/install.ts` states that dispatcher routes by its policy rather than by the environment, and Node samples the proxy environment at start — so a plugin mounting later cannot redirect it. Verified three ways on Node 22 with `scripts/host-egress-probe.mjs`: a mid-process `process.env` write moved nothing, an explicitly installed global dispatcher WAS observed by a recording proxy (control), and `NODE_USE_ENV_PROXY=1` set at launch did not make the lookup per-request. **Consequences for issue #22:** the report's `Connection error. / TRANSPORT` was not produced by this policy, and the `llm/stream` listener shipped in 0.6.19 (`ctx.on('llm/stream', …)`, `llmStream`/`diagnosedLlmStream` in `src/runtime.ts`) can only fire when a blocked CHILD connection coincides within its 1 s window with an unrelated model failure — it misattributes rather than diagnoses, so its removal (and the rationale comment at its registration site) is queued for the next release. The claim that stood here before ("the harness's own LLM transport is adjudicated by this policy too") was wrong, as was the README text it produced; the five-language READMEs now carry the corrected known-limitations bullet. **Unaffected and still true:** `ctx.llm.listProviders()` exposes provider ids/names only (`LlmProviderInfo` carries no endpoint), configured base URLs live in adapter-owned settings profiles (`LlmConfigurableProvider` names a `settingsNs`/`settingsPath`, never a field), and there is no per-spawn environment seam for shell children (the subprocess service builds the child environment internally and the only per-execution registry, `ctx.shellEnv`, accepts `DSH_*` keys only).
- IP matching normalizes spellings before comparing: an IPv4-mapped IPv6 literal (dotted `::ffff:169.254.169.254`, hex `::ffff:a9fe:a9fe`, full `0:0:0:0:0:ffff:a9fe:a9fe`) is unmapped to its dotted IPv4 form on BOTH sides — candidate addresses and rule patterns (`unmapIpv4` in `src/rules.ts`, applied by `ipMatches`, `literalIpOf`, and `compileIpPattern`) — so an IPv4 `ips` rule (literal, glob, or CIDR) cannot be bypassed by the mapped spelling, and a mapped pattern also covers the plain IPv4 form. End-to-end guards live in `test/proxy.spec.ts` (plain-HTTP and CONNECT, literal and CIDR rules) next to the matcher-level case in `test/network.spec.ts`; the `ips` row of both `rules-format` docs states the normalization.
- The proxy connects on the ADJUDICATED address, never a second resolution: `decideWithResolution` returns the target carrying the resolved addresses, `connectUpstream` tries those addresses in order for CONNECT tunnels (502 when none accepts) and REFUSES to dial the hostname when the adjudication resolved no address (issue #21 — dialing by name is a second resolution whose answer the rules never saw, and it is the one path where Node's happy-eyeballs race applies, with its 250 ms `autoSelectFamilyAttemptTimeout` default that an IP-literal connect skips entirely), and the plain-HTTP forward pins `http(s).request` with a `lookup` that answers from the same list whenever the adjudication found addresses — so a hostname that re-resolves between adjudication and connect (DNS rebinding) cannot reach an address the rules never approved, while a multi-address host keeps its fallbacks.

## Build

`typescript` + `tsdown` are regular `dependencies` on purpose: pnpm does not install devDependencies of git-hosted packages, and the git channel's `prepare` must build with production dependencies alone. `scripts/prepare.mjs` is the single build entry; it runs tsdown FIRST, then tsc declarations into `lib/types` — tsdown's `clean: true` wipes `lib/`, so the reverse order would delete the fresh declarations.

The repo's `pnpm-workspace.yaml` declares `allowBuilds: { esbuild: true }`: pnpm's isolated prepare env for git-hosted packages reads the dependency's shipped workspace file, and without that entry both local installs and git installs fail with `ERR_PNPM_IGNORED_BUILDS` on esbuild's (harmless platform-binary validation) postinstall. The package.json `pnpm` field is NOT usable for this — pnpm 11 ignores it. Git users still need the single `allowBuilds` key for `dsh-permission-rules` itself, which the `dsh` CLI prints verbatim.

## Integration dependency

`test/integration.spec.ts` imports `dsh-auto-review` from `vendor/dsh-auto-review-0.12.1.tgz` — a COMMITTED build artifact of the sibling repo (regenerate with `pnpm --dir ../dsh-auto-review pack --pack-destination <this repo>/vendor`). It must stay in the tree because the git install channel's isolated `prepare` installs devDependencies and would fail on a missing `file:` target. The shipped tarball carries runtime JS without `.d.ts`, so `tsconfig.test.json` maps the package name onto `test/auto-review.d.ts` for types while runtime resolution loads the real bundle.
